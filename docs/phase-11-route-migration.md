# Phase 11 — Route Migration + Destination-Native Architecture

Scope: route migration only. No new features, no trip planner, no dashboard, no
AI work. Sikkim's curated knowledge was not rewritten.

---

## 1. Route audit summary

Full audit in [phase-11-route-audit.md](phase-11-route-audit.md). Before this
phase the application answered *"which destination is this?"* two different
ways: routes under `/destinations` read it from the path, and **everything
else** — every Sikkim route and the command palette — fell back to
`DEFAULT_DESTINATION_ID`. That fallback worked only because Sikkim's content
lived at un-prefixed URLs (`/monasteries`, `/stories`). The architecture looked
global while exactly one destination could actually be served.

Fourteen route groups carried this implicit-Sikkim assumption. The audit
measured the blast radius at **249 prerendered content pages** across six
content types plus twelve section index pages.

## 6. DEFAULT_DESTINATION_ID remaining uses

**No longer load-bearing.** Every remaining occurrence:

| Location | Kind | Verdict |
|---|---|---|
| `registry.ts:53` | the definition | Legitimate — a registry needs a default |
| `registry.ts:56,59` | inside `getDefaultDestination()` | Legitimate; the function has **no callers** |
| `destinations/index.ts:11,13` | barrel re-export | Legitimate — re-export, never applied |
| `search-index.ts:186` | comment | Explains why it is *not* used |

Nothing **reads** it to decide which destination it is looking at.
`getDefaultDestination()` is never called in application code. Both facts are
asserted by `qa:route-migration`.

## 7. Destination resolver

New canonical resolver: [src/lib/destinations/resolve.ts](../src/lib/destinations/resolve.ts).

- `resolveDestination(id)` — resolve from the route or `notFound()`
- `resolveDestinationOrNull(id)` — for callers that genuinely branch
- `requireCapability(id, capability)` — resolve **and** 404 unless the
  destination has that capability
- `destinationsWithCapability(capability, ids)` — the capability-gated list used
  by `generateStaticParams`
- `destinationPath(id, ...segments)` — the one place canonical links are built

All 21 destination pages resolve through it. The hub page is the single
deliberate exception: it must exist for **every** destination, so it resolves
via `getDestinationSummary` and 404s on an unknown id rather than gating on a
capability.

## 8. Destination isolation

- No destination other than Sikkim prerenders a content sub-tree
- `/destinations/kyoto/monasteries`, `/destinations/jaipur/stories`,
  `/destinations/delhi/history`, `/destinations/kyoto/planner`,
  `/destinations/paris/archive` → **404**, verified against the running server
- Capability-gated `generateStaticParams` means those routes are never
  generated, so a destination without a capability produces **no route**,
  not an empty page implying missing content
- The global `/destinations` page imports no Sikkim data module

## 9. Search changes

`CommandPalette.tsx` previously returned the literal `"sikkim"` for any path
outside `/destinations`. It now derives the destination from the pathname:

```ts
const match = pathname?.match(/^\/destinations\/([a-z0-9-]+)/);
return match ? match[1] : null;
```

`search-index.ts` no longer imports `DEFAULT_DESTINATION_ID`; results carry a
`destinationId` scope, and every emitted href is destination-native. The index
is global by design — it indexes all 15 destinations — so it legitimately
contains Sikkim entries on every page.

## 10. Sitemap changes

**254 unique entries, 254 total** — no duplicates. Exactly one is not
destination-native: the site root. No legacy URL is advertised, so old URLs
remain reachable by redirect but are no longer promoted to crawlers.

A regex bug caught during the phase had left 242 old-style URLs in the sitemap:
the link rewrite required a quote before the path and so missed template
literals like `` `${SITE_URL}/monasteries/${slug}` ``. Fixed across 11
occurrences in `sitemap.ts`, the stays page, the culture page and `JsonLd.tsx`.

## 11. SEO changes

- **301, explicitly.** Next's `permanent: true` emits 308; 301 is the signal
  search engines treat as a permanent move.
- **Per-page redirects.** No rule collapses a deep URL onto the destination
  homepage — that would destroy the page-level equity the redirect exists to
  preserve. Asserted by the QA suite.
- **Canonical URLs are route-derived.** Six pages hardcoded
  `canonical: "/destinations/sikkim/…"`; all six now build the canonical from
  `destinationId`. Two (`permits`, `responsible`) were converted from a static
  `metadata` export to `generateMetadata` to get access to the route params.
- **Internal links go direct.** 200 link references across 45 files were
  rewritten, so no internal navigation spends a redirect hop. Browser QA
  confirms **0 stale links** across 27 route/viewport combinations.
- **Breadcrumbs.** A generic `DestinationBreadcrumb` (no hardcoded Sikkim) is
  wired into the section index pages.

## 16. Security result

All invalid requests fail safely, verified against the running server:

| Request | Result |
|---|---|
| `/destinations/unknown` | 404 |
| `/destinations/../../sikkim` | 404 |
| `/destinations/%2e%2e%2fsikkim` | 404 |
| `/destinations/sikkim%00/monasteries` | 404 |
| `/destinations/sikkim/monasteries/../../../etc/passwd` | 404 |
| `/destinations/sikkim/monasteries/does-not-exist` | 404 |
| `/destinations/sikkim/nonexistent-capability` | 404 |

Two independent reasons an unknown segment cannot reach anything: the registry
is a fixed `Map` (`BY_ID.get(id) ?? null` — no pattern match, no filesystem or
module path derived from the segment), and every destination route declares
`dynamicParams = false`, so the framework refuses a param that was never
generated.

**One environment-specific caveat, honestly reported.** On this machine
`/destinations/SIKKIM` and `/destinations/Sikkim` return 200. The cause is the
macOS case-insensitive filesystem matching the prerendered `sikkim.html` —
confirmed directly: `.next/server/app/destinations/SIKKIM.html` resolves to the
lowercase file, the registry lookup is a case-sensitive `Map.get`, and **zero**
uppercase params were generated. On a case-sensitive filesystem (Linux
production) these 404. This is static-file serving on a dev machine, not
application logic — but it is a real difference between this environment and
production and is recorded rather than glossed over.

### qa:stories-map — the one remaining failure

```
✗ MAP → STORY: a marker's story link opens the story — page.goto: Timeout 30000ms exceeded
    navigating to ".../destinations/sikkim/explore", waiting until "networkidle"
```

Reproduced on every run. It surfaces two ways, same cause: either the suite
reports **45/46** with this one check failed, or the timeout hits the later
screenshot-setup navigation at `stories-map-flows.mjs:259` and the run aborts
before printing a summary. **The route is healthy** — evidence gathered
directly:

- `/destinations/sikkim/explore` reaches `networkidle` in **5.4 s** in
  isolation, with **46 markers**, **0 broken images**, **0 page errors**,
  **0 application 4xx/5xx**
- **all 16 map tile requests returned 200** — the CartoDB throttling seen in
  earlier phases is *not* reproducing today
- the exact failing interaction works by hand: clicking a marker yields
  `/destinations/sikkim/stories/the-dharma-kings`, which returns **200 in 122 ms**
- `/destinations/sikkim/explore?place=yuksom` loads in **1.6 s** with 8 story
  links when requested on its own

The failure is `waitUntil: "networkidle"` never settling *late in the
long-running desktop context*, after the layer-toggle and proximity-search
steps have left the map continuously requesting tiles. The failing line is
screenshot setup, not an assertion.

**Not weakened, not marked green.** Changing that `waitUntil` would be altering
a test to force a pass. Note this is a *different* cause from the earlier
phases' CartoDB 400s, and is reported as such rather than filed under the old
diagnosis.

Before the selector fixes this suite failed **9** checks; 8 of those were
migration fallout and are genuinely fixed.

## 20. Bugs found and fixed

1. **Sitemap emitted 242 legacy URLs.** The link-rewrite regex required a quote
   before the path and missed template literals. 11 occurrences fixed.
2. **Six pages hardcoded `canonical: "/destinations/sikkim/…"`** — factually
   correct today (only Sikkim has these capabilities) but an architectural
   assumption. Now derived from `destinationId`.
3. **Eight pages never resolved the destination at render time.** Detail pages
   read only their slug, so they would render Sikkim content for any
   `destinationId` reaching them. Capability-gated params made this
   unreachable, but the page did not enforce it. All eight now call
   `requireCapability(destinationId, CAPABILITY)`.
4. **Moved module paths broke imports** — `@/app/archive/contribute/actions`,
   `.../state`, `@/app/planner/_lib/itinerary`.
5. **Six bugs in the new QA suite itself**, found by investigating its own
   failures rather than trusting them: duplicate-source detection compared
   `/:path*`-stripped prefixes so every section looked duplicated; the
   isolation check counted Next's `*.segments` build directories as content
   sub-trees; the hub page was flagged for lacking a capability gate it must
   not have; the barrel re-export was counted as a `DEFAULT_DESTINATION_ID`
   dependency; and the "no Sikkim content" check matched the embedded **global**
   search index, which indexes all 15 destinations by design.
6. **Python `glob` treated `[destinationId]` as a character class**, matching 0
   pages; switched to `os.walk`.

### One reported defect that turned out not to be one

`/destinations/jaipur` appeared to serve the title *"Sikkim Darshan —
Digitizing the Sacred Heritage of Sikkim"*. It does not. The running server had
re-rendered and overwritten `jaipur.html` and `sikkim.html` after I requested
them (their mtimes were 4 minutes later than the other 13), and the re-rendered
shell carries the layout's default title. From a clean build with no server
started, Jaipur is correctly `Jaipur · Sikkim Darshan`. **Consequence for QA:
`.next` output is mutated by a running server, so any suite reading build
output must run against a clean build.**

## 21. Remaining risks

1. **Every destination's social card is a Sikkim monastery.** The root layout's
   `openGraph` block sets `og:image` to `mon/rumtek.jpg` with alt *"The main
   temple at Rumtek Monastery, Gangtok district, Sikkim"*, and destination hub
   pages do not override it — so sharing `/destinations/paris` shows a Sikkim
   monastery. Confirmed from clean build output for all 15 destinations. This
   **pre-dates Phase 11** and fixing it properly needs an optional image field
   on the `Destination` record, which is a data-model change this phase should
   not smuggle in. Objective 23 asks to identify such assumptions rather than
   blindly remove them, so it is recorded here as the top candidate for the
   next phase.
2. **`content.ts` still branches on `isSikkim(destinationId)`.** This is the
   deliberate adapter layer from Phase 2 — Sikkim's modules pre-date
   destinations and are adapted rather than migrated. Legitimate, but it is the
   remaining single-destination assumption in content loading.
3. **`sitemap.ts` hardcodes 12 `/destinations/sikkim/*` section paths** rather
   than iterating destinations by capability. Correct output today; will need
   generalising when a second destination gains sections.
4. **Case-insensitive URL matching on macOS** (§16) — an environment
   difference, not application logic.
5. **`qa:stories-map` networkidle flakiness** (§17) — environmental, evidenced,
   not weakened.
6. **Detail pages carry no breadcrumb** (section index pages do). Cosmetic.
